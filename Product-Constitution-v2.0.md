# Product Constitution v2.0 — Publisher Blueprint™

**Status:** Active  
**Owner:** Jeff Hallstead  
**Purpose:** Every PRD, ADR, and implementation decision in this product must comply with this constitution. It is the single source of truth for brand, taxonomy, naming, messaging, data, and engineering standards.

---

## 1. Brand architecture

### 1.1 Identity hierarchy

```text
Publisher Blueprint™
  └── Publisher OS™
  └── Publisher Index™
  └── Publisher Copilot™

Secondary endorsement: "by Jeff Hallstead"
```

- **Publisher Blueprint™** is the primary product identity: the $99 one-time strategic assessment and plan.
- **Publisher OS™** is the recurring operating layer: $49/month for running the plan, progress tracking, and unlimited Copilot use.
- **Publisher Index™** is the proprietary scoring methodology.
- **Publisher Copilot™** is the AI strategic advisor.
- The founder's consulting website is a separate brand and may not dictate the SaaS aesthetic.

### 1.2 Positioning

The product is a self-serve executive strategy platform, not a quiz, marketing assessment, or lead magnet. It should feel like a premium SaaS dashboard (Linear, Notion, Stripe Dashboard, Vercel) with generous whitespace, minimalism, and an executive aesthetic.

### 1.3 Voice and tone

- Confident but not arrogant.
- Diagnostic, not prescriptive to the point of false certainty.
- Action-oriented; every diagnosis must terminate in a concrete next step.
- No hype, no invented figures, no guaranteed outcomes.
- The product speaks to marketing, brand, and communications leaders at B2B companies in the $10M–$1B revenue range with teams of 3–50 marketers.

## 2. Design system

The design system is **Executive Obsidian**: near-black surfaces with an indigo-violet product accent.

- Surfaces: `#09090b`, `#0a0a0b`, `#111113`.
- Primary accent: `#6366f1` (indigo-violet).
- Secondary accent: `#a78bfa` (soft violet).
- Typography: **Plus Jakarta Sans** (body), **Outfit** (display / wordmark), **DM Mono** (eyebrow / technical).
- No hardcoded color utilities in components. All colors must be semantic tokens (`bg-surface`, `text-primary`, `text-brass`, etc.) defined in `src/styles.css`.
- Components must be shadcn/Tailwind v4 compatible and use `@theme` tokens.
- Full design system reference: `/design/Design-System.md`.

## 3. Naming conventions

### 3.1 Files and routes

- React components: PascalCase (`ScoreCard.tsx`, `AppShell.tsx`).
- Route files: TanStack Start file-based convention (`index.tsx`, `_authenticated/dashboard.tsx`, `api/public/webhook.ts`).
- Server functions: `*.functions.ts` (client-safe wrappers) and `*.server.ts` (server-only helpers).
- Library modules: camelCase for config files, kebab-case for directories.
- PRD files: `Phase-XX.md` with zero-padded two-digit numbers.
- ADR files: `ADR-XXX-Short-Title.md` with sequential three-digit numbers.

### 3.2 Database

- Tables: `snake_case`, plural, in the `public` schema.
- Columns: `snake_case`.
- Enums: `snake_case`.
- Functions: `snake_case` in `public`.
- The `auth` schema is reserved for Supabase auth and never modified.
- Primary keys are UUIDs generated by `gen_random_uuid()`.

### 3.3 Product identifiers

- Use `Publisher Blueprint™` (not "Owned Audience Blueprint").
- Use `Publisher OS™` (not "Operating System").
- Use `Publisher Index™` (not "Score" or "Assessment Score").
- Use `Publisher Copilot™` (not "AI chat" or "assistant").

## 5. Messaging principles

1. **Lead with the diagnosis, then the action.**
2. **Never promise outcomes.** Use "can improve," "is likely to," "reduces risk of" rather than "will increase X%."
3. **State assumptions explicitly.** AI outputs must label what is assumed versus known.
4. **No invented figures.** If a number is not in the input, do not invent one.
5. **Every level description must include the next concrete step.** The user should always know what to do next.
6. **Feature names are branded.** Use the Publisher™ product taxonomy, not generic labels.

## 6. Database naming standards

### 6.1 Schemas

- `public` — application tables, functions, and enums.
- `auth` — Supabase-managed auth; read-only for application code.
- `storage`, `realtime`, `supabase_functions`, `vault` — reserved; never modified.

### 6.2 Table creation pattern

Every `public` table must follow this exact order:

1. `CREATE TABLE public.<name>`
2. `GRANT` statements to `authenticated`, `service_role`, and `anon` only where required.
3. `ALTER TABLE public.<name> ENABLE ROW LEVEL SECURITY`
4. `CREATE POLICY` for the required access patterns.

### 6.3 Standard columns

All tables should include:
- `id uuid primary key default gen_random_uuid()`
- `created_at timestamp with time zone default now()`
- `updated_at timestamp with time zone default now()` (with update trigger)
- `user_id uuid references auth.users(id)` for user-scoped rows

### 6.4 Reserved enums

- `app_role` (`admin`, `user`)
- `assessment_status` (`draft`, `in_progress`, `completed`)
- `lifecycle_stage` (`visitor`, `registered`, `assessment_started`, `assessment_completed`, `blueprint_owner`, `os_subscriber`, `churned`)
- `qualification_tier` (`unqualified`, `lead`, `marketing_qualified`, `sales_qualified`, `customer`)

## 7. Event naming conventions

All business events are recorded in the immutable `platform_events` table.

- Names are lowercase, past tense, and dot-namespaced: `domain.thing_happened`.
- Version numbers are declared in `src/lib/events/catalog.ts` and incremented when a payload shape changes.
- Legacy backfilled events carry a `legacy.` prefix and version `0`.
- Events must be emitted from a single canonical catalog; ad-hoc event names are prohibited.
- Major domains: `organization`, `assessment`, `blueprint`, `commerce`, `copilot`, `analytics`, `recommendation`, `lifecycle`, `qualification`.
- Full event schema: `/api/Event-Schema.md`.

## 8. AI design principles

1. **Grounded context.** Every AI request rebuilds a briefing from the user's own assessment, blueprint, roadmap, and prior documents. The client cannot spoof context.
2. **Honesty rules.** State assumptions, never guarantee outcomes, never invent figures.
3. **Directional, not predictive.** Simulations model up/down/flat scenarios; they do not predict a numeric score.
4. **Structured outputs.** Generated deliverables use strict `json_schema` structured outputs to ensure required fields.
5. **Single model provider.** The default model is `google/gemini-3.6-flash` via the Lovable AI Gateway, declared in one place so swaps are localized.
6. **Human-in-the-loop.** Generated documents are versioned and regenerable; chat sessions are editable and resumable.

## 9. Engineering standards

### 9.1 Stack

- **Framework:** TanStack Start v1
- **React:** 19
- **Build:** Vite 7
- **Styling:** Tailwind CSS v4 with `@theme` tokens in `src/styles.css`
- **Data:** TanStack Query
- **Backend:** Lovable Cloud (Postgres + Auth + RLS)
- **AI:** Lovable AI Gateway

### 9.2 Server boundaries

- App-internal logic uses `createServerFn` from `@tanstack/react-start`.
- Public webhooks, cron, and external APIs use TanStack file routes under `src/routes/api/public/*`.
- Protected server functions use `.middleware([requireSupabaseAuth])` and never run from public route loaders.
- Admin clients (`supabaseAdmin`) bypass RLS and are loaded dynamically only after role verification.
- `process.env` values are read only inside handlers.

### 9.3 Client boundaries

- Browser-only libraries (e.g., maps, heavy charting) must be dynamically imported after hydration.
- Supabase client for browser imports from `@/integrations/supabase/client`.
- No secrets, API keys, or private credentials in client bundles.

### 9.4 Security

- RLS is the primary authorization boundary. Paid payloads are never sent to unentitled clients.
- Roles live in a separate `user_roles` table and are checked via a security-definer `has_role` function.
- Integration credentials are encrypted with AES-256-GCM at rest.
- Webhook signatures must be verified before processing.

### 9.5 Component standards

- Use semantic tokens; never hardcode colors.
- Use shadcn primitives and project variants.
- Keep components small and focused; business logic belongs in `src/lib/` or server functions.
- Every route parent component must render `<Outlet />`.

### 9.6 Design and exports

- No `tsc --noEmit` for type checks; use `tsgo`.
- Run tests via `bunx vitest run` or `lovable-exec test`.
- Keep server-function files as thin wrappers: imports, types, and exported declarations only; move helpers to `*.server.ts`.

## Compliance

A PRD is considered compliant with this constitution when it:

- Uses the product taxonomy defined in Section 4.
- References the design system in Section 2 and `/design/Design-System.md`.
- Proposes database changes that follow Section 6.
- Defines events that follow Section 7.
- Describes AI behavior that follows Section 8.
- Specifies implementation that follows Section 9.

Violations must be resolved during PRD review before implementation begins.
